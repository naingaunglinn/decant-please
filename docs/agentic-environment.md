# Agentic engineering environment — design

How this repo is set up so an agent can work in it with direction rather than supervision.
The premise: don't write better prompts, build a better environment. A prompt is a
temporary instruction; the repo is a durable one.

---

## 1. Requirements

**Functional**

- An agent picks up a task and knows, without being told: what the product is, what the
  rules are, what it may touch, how to prove it worked, and how to ship it.
- Directory-scoped context — a backend task does not load UI token rules.
- A failing check is legible enough that the agent self-corrects instead of escalating.
- Every tool works: Codex, Claude Code, Cursor. No tool-specific fork of the rules.

**Non-functional**

- Always-on context stays small. Target under ~200 lines at the root.
- No generated documentation, no build step, no pre-commit hook. One maintainer.
- Nothing is deleted in the migration — history moves, it doesn't vanish.
- The existing `prompts/` + WORKFLOW loop keeps working unchanged; this wraps it.

**Constraints**

- Solo maintainer, so anything requiring two copies of a fact will rot.
- Tests run on SQLite, production on Postgres 17 — the harness must cover that gap.
- Browser checks need a running stack, so they cannot live in CI as currently built.
- `frontend/AGENTS.md` contains a vendored block regenerated by Next.js tooling.

## 2. High-level design

```
                              ┌───────────────────────────┐
        TASK  ───────────────▶│  1. SPEC                  │
   (issue / prompts/NN-*.md)  │  PRODUCT.md + step file   │
                              │  WHO WHY WHAT RULES        │
                              │  NON-GOALS DONE            │
                              └────────────┬──────────────┘
                                           ▼
   ┌───────────────────┐       ┌───────────────────────────┐
   │ ALWAYS-ON CONTEXT │──────▶│  2. MAP                   │
   │ AGENTS.md (root)  │       │  agent reads repo, returns│
   │  ├ backend/       │       │  architecture, affected   │
   │  └ frontend/      │       │  files, contract, sequence│
   │ + .claude/skills  │       │  risks, verification plan │
   └───────────────────┘       │  ── NO CODE YET ──        │
            │                  └────────────┬──────────────┘
            │  boundaries                   ▼ human approves plan
            │  (§5 envelope)   ┌───────────────────────────┐
            └─────────────────▶│  3. BUILD                 │
                               │  one vertical slice       │
                               │  inside the envelope      │
                               └────────────┬──────────────┘
                                            ▼
                               ┌───────────────────────────┐
              ┌───────────────▶│  4. PROVE  (VERIFY.md)    │
              │                │  composer test            │
              │   failure      │  typecheck + lint         │
              │   feeds back   │  verify-*.mjs (browser)   │
              └────────────────│  postgres-portability.sh  │
                               └────────────┬──────────────┘
                                            ▼ green + evidence report
                               ┌───────────────────────────┐
                               │  5. LEARN                 │
                               │  repeated correction →    │

                               └───────────────────────────┘
```

## 3. Components

| Component | File(s) | Loaded | Answers |
|---|---|---|---|
| Product spec | `PRODUCT.md` | on demand | what should exist, and what must not |
| Always-on rules | `AGENTS.md` + `CLAUDE.md` pointer | every turn | how to work here |
| Scoped rules | `backend/AGENTS.md`, `frontend/AGENTS.md` | on entering that tree | stack conventions |
| Step specs | `prompts/NN-*.md` | when named | this task in detail |
| Process | `prompts/WORKFLOW.md` | when shipping | issue → branch → PR |
| Verification contract | `VERIFY.md` | at PROVE | what counts as proof |
| Reusable workflows | `.claude/skills/*` | on trigger | money rules, accounting |
| History | `CHANGELOG.md` | on demand | why it is like this |
| Harness | `composer test`, `verify-*.mjs`, `verify-postgres-portability.sh`, CI | at PROVE | did it actually work |

## 4. Context flow — the real design decision

The scarce resource is attention, not disk. Today `CLAUDE.md` puts ~8,600 words in front
of the model on every turn, 67% of it superseded changelog. The redesign routes context
by **when it is needed**:

```
every turn        AGENTS.md                        ~140 lines
entering backend/ + backend/AGENTS.md              ~110 lines
entering frontend/+ frontend/AGENTS.md             ~130 lines
task names it     + PRODUCT.md or prompts/NN-*.md  as needed
at PROVE          + VERIFY.md                      ~90 lines
archaeology only  CHANGELOG.md                     594 lines, never automatic
```

A backend task now loads roughly 250 lines of highly relevant rules instead of 893 lines
that are two-thirds history and one-third mixed frontend/backend.

## 5. The verification harness

This is the half that makes agentic work safe, and the half with the real gap.

**What exists and is good:** 20 Feature tests; a Postgres portability script that catches
the SQLite/Postgres `LIKE` and `ORDER BY` divergence this project has already shipped as
a bug; four Playwright scripts producing genuine browser evidence at four viewports;
two-job CI wired to the Heroku deploy gate.

**What is missing:**

| Gap | Fix |
|---|---|
| Frontend has no `typecheck` script — `tsc` is installed but never run | add `"typecheck": "tsc --noEmit"` |
| Frontend has no `test` script — Playwright is a dependency with no entry point | add `"verify"` aggregating the fixture-free scripts |
| The `verify-*.mjs` scripts are undiscoverable — no index, no npm script, no doc | `VERIFY.md` + `frontend/AGENTS.md` table |
| Nothing says which check to run for which change | `VERIFY.md` tier table |
| Browser checks never run in CI (they need a live stack) | keep them local, but make them a Definition-of-Done checkbox |

**Design principle:** the agent should hit the failure, not the human. Each check exits
non-zero with a specific message, so "run tests, investigate failures, fix root cause,
repeat until green" is a loop the agent can close by itself. Note that
`verify-image-fallback.mjs` reports SKIP rather than passing vacuously — that honesty is
what makes an agent-facing harness trustworthy, and new checks should follow it.

## 6. Boundaries

The permission envelope is prose today, enforced by review rather than tooling. Each task
declares CAN TOUCH / DO NOT TOUCH; `AGENTS.md` § 5 gives the default.

The high-value entries are the ones where damage is silent:

- **shipped migrations** — editing one desyncs every environment that already ran it
- **`app/Enums/**`** — a value change orphans stored rows
- **`globals.css` `@theme`** — a token change repaints every surface at once
- **`lib/types.ts`** — drifts from the API Resource and the failure surfaces at runtime
- **`components/ui/**`, `components/layout/**`** — blast radius is the whole storefront

This is deliberately not enforced in tooling yet. Prose boundaries plus a diff review
are proportionate at this size; file-level permissions become worthwhile at L4/L5 below.

## 7. Capability ladder — where this repo sits

```
L1 Prompt          ████████████  prompts/ — 26 step specs. Strong.
L2 AGENTS.md       ████░░░░░░░░  root is Claude-only + 67% changelog; backend has none.
L3 Skills          █████░░░░░░░  3 skills, but 2 are generic third-party SaaS finance.
L4 MCP             ░░░░░░░░░░░░  none.
L5 Subagents       ░░░░░░░░░░░░  none — correct. Do not start here.
```

**L2 is the whole job right now.** Fixing it is what this design does.

**L3, once L2 lands:** `decant-money` is the model to copy — narrow, project-specific,
triggered by a task shape. Two more earn their place: a **postgres-portability** skill
(the SQLite/Postgres divergence and how to check it) and a **filament-resource** skill
(the `Resources/{Thing}/{Pages,Schemas,Tables}` shape, since new resources are the most
repeated backend task here). The two vendored SaaS finance skills are for running the
business, not building it — consider moving them out of the repo's skill path so they
stop competing for trigger attention.

**L4 MCP:** only two candidates are worth it — a Postgres MCP for read-only inspection of
local data during debugging, and GitHub for issue/PR context. Both are read-heavy and
low-risk. Not urgent.

**L5 Subagents:** not until one agent is reliably passing the DoD unaided. The plausible
first split is a verifier subagent that only runs `VERIFY.md` and reports — bounded
delegation with no write access.

## 8. Trade-offs made explicit

| Decision | Gains | Costs |
|---|---|---|
| Split one context file into five | ~85% less always-on context; scoped loading | five files to keep current; drift risk |
| Changelog to `CHANGELOG.md` | stops paying for history every turn | a habit change in WORKFLOW step 5 |
| Prose boundaries, not tooling | zero setup, proportionate to one maintainer | relies on review discipline |
| Browser checks stay local | they need a real stack; CI would need compose + seeded data | someone must remember to run them; mitigated by the DoD checkbox |
| Keep `prompts/` unchanged | the loop works and is well documented | numbered step files don't map cleanly to ad-hoc bug work |

## 9. What to revisit as this grows

- If the storefront gains a second locale or a second surface, `PRODUCT.md` may need
  splitting per surface.
- If browser checks start catching real regressions often, move them into CI behind
  `docker compose up` with a seeded database — the cost becomes worth it.
- If `backend/AGENTS.md` passes ~200 lines, split Filament out.
- If more than one person works in the repo, prose boundaries stop being sufficient and
  CODEOWNERS plus branch protection should carry the load instead.
